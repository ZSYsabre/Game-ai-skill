# 游戏分析框架

## 选择角度

先写出文章要回答的一个问题，再选择能直接解释它的分析轴。每篇使用两到三个即可。

| 分析轴 | 关键问题 | 优先证据 |
| --- | --- | --- |
| 核心玩法 | 玩家反复做什么，动作怎样产生反馈 | 实际流程、教程、关卡、操作记录 |
| 信息与叙事 | 玩家按什么顺序知道事情，信息怎样改变判断 | 页面、对白、档案、任务顺序、结局条件 |
| 视听与界面 | 画面、声音和界面怎样影响操作与气氛 | 实际素材、UI流程、可访问性与设备表现 |
| 难度与引导 | 玩家在哪里理解规则，哪里容易卡住 | 新手流程、提示、失败反馈、玩家讨论 |
| 制作条件 | 人数、周期、预算和工具怎样影响成品 | 开发日志、访谈、版本记录、人员分工 |
| 技术实现 | 系统为何能运行，限制如何进入玩法 | 开源代码、技术分享、漏洞、性能表现 |
| 题材与文化 | 游戏为何让特定玩家产生熟悉或陌生感 | 地域细节、语言、民俗、生活经验 |
| 产品与传播 | 玩家怎样接触、购买、分享和持续讨论 | 商店页、平台数据、主播传播、社区内容 |
| 商业与维护 | 谁付钱，更新由谁完成，长期成本在哪里 | 定价、授权、更新记录、服务与社区管理 |

## 组织文章

### 作品解析

先用一段让读者进入游戏，再沿玩家操作解释规则。随后挑出最影响体验的一处设计，补叙事、视听或难度的原因与后果。

### 开发复盘

先写创作者的条件和目标，再按构思、原型、制作、测试、发布的实际顺序推进。工具只在它改变时间、成本或成品时展开。

### 行业观察

先写已经发生的案例，再比较谁因此多了一种选择，谁多承担了一项工作。结论写到证据允许的位置。

## 控制剧透

- 无剧透只介绍设定、核心循环和公开宣传内容。
- 轻度剧透可以写中前段机制与题材变化，不公开关键身份、终局选择和谜底。
- 深度解析可以讨论完整流程，开头明确提示剧透范围。

## 判断是否有效

有效分析会改变读者对游戏的理解。例如，简陋网页为何增强恐怖感，低技术门槛为何扩大玩家范围，某个Bug为何暴露开发方式的限制。

只描述“画面很好”“剧情不错”“AI提高效率”仍然不够。继续补具体对象、发生环节与可观察后果。
